VSD Student Learning Workspace — Initial Specs

PRODUCT

Build a learning application organized into three tabs:

A. Workspace tab (student-facing)
B. Prompts tab (student / instructor / researcher)
C. Versions tab (student / instructor / researcher)

The Prompts and Versions tabs are for the people participating in the learning experience, and for students.
Placeholders are acceptable for the initial version, but each tab should have its basic structure in place.

Students see and edit the prompts because they take part in shaping the norms, rules, and prompts
that guide the AI tutor, and doing so teaches them how to prompt AI. The prompts are fully transparent
and nothing is locked: a student could remove a rule such as "do not give away the answer". We trust
them not to.


A. WORKSPACE TAB

Three coordinated areas:

1. Learning workspace on the left
   - Hosts learning and activity modules.
   - Owns the current lesson or activity content.
   - Shows the lesson introduction, a card for the current activity, and the list of activities.
   - The card is a flat white box beside the activity list (stacked above it when the panel is narrow).
     It shows "Step N of M", the activity title, its description (the prompt), and its learning objectives.
     Activities do not repeat the prompt in the activity panel; the panel header shows "Step N · Title".
   - A "Next" button under the activity list moves to the next activity (hidden on the last one).
     If the current activity's work hasn't been checked since it last changed, Next first offers
     "Check my work" (feedback appears; the student stays on the step) or "Skip to next step".
     Once checked, Next moves on directly.
   - The current lesson is VSD stakeholder analysis: each activity is one step of the process (see
     STAKEHOLDER TOKENS LESSON below).

2. AI feedback panel on the right
   - Reserved for feedback about the student's work in the learning workspace.
   - For the initial version, use placeholder content or mock data only, clearly labeled as placeholder.
   - Keep the panel independent so a real AI feedback source can be connected later.
   - Feedback is requested on demand (e.g. a "Check my work" action), not on every change.
   - Each feedback item may point to a specific part of the student's work (a diagram node or an annotated region).
   - Students can rate feedback as helpful / not helpful (placeholder for now).

3. Activity panel along the bottom
   - Displays interactive content for the current activity.
   - Different activities may provide different interactions, including:
     - Composing diagrams by placing and connecting items.
     - Hovering over, highlighting, and annotating parts of a visual.
   - Treat this as a host for activity-specific components, not as one universal canvas.

Scrolling layout and resizable panels:
   - The workspace scrolls like a page. By default the learning workspace and feedback panels show their
     full content; the activity panel sits below them and is reached by scrolling.
   - Students can resize panels by dragging dividers:
     - A vertical divider between the learning workspace and the feedback panel (feedback width).
     - A horizontal divider between the top panels and the activity panel (top panels' height, min 120px).
       By default the top panels fit their content; dragging up makes them shorter (they scroll inside)
       and moves the activity panel up. Resetting returns to fitting their content.
     - A horizontal divider along the bottom edge of the activity panel (activity height, 240–4000px,
       default 520px). Making it taller makes the page longer.
   - Dividers are keyboard accessible: focus with Tab, Arrow keys resize, Enter resets.
     Double-clicking a divider resets it to the default size.
   - An "Expand" button in the activity panel's header makes it fill the visible area and scrolls to it;
     "Restore" returns to the previous height.
   - Inside the diagram, the mouse wheel scrolls the page (it does not zoom); zoom with the +/− controls or pinch.
   - Panel sizes are remembered per browser (a UI preference, not student data).
   - On narrow screens (800px wide or less) the panels stack vertically; the feedback width can't be
     resized there, but the activity height still can.


STAKEHOLDER TOKENS LESSON

The lesson walks through VSD stakeholder analysis (Friedman, Kahn & Borning) using a digital version of
Stakeholder Tokens (Yoo, 2018). Each activity in the learning workspace is one step; the activity panel
holds one token board that all steps share, so the student builds a single map across the lesson.

Steps (each one adds tools to the board; earlier tools stay available, so students can revise):
  1. Choose a starting point — name the technology, value, or context of use at the centre of the board.
  2. Direct stakeholders — people who interact with the technology or its outputs.
  3. Indirect stakeholders — people affected without using it; mark excluded stakeholders and flag
     hidden or overlooked ones.
  4. Relationships — connect stakeholders who affect one another, with a label ("cares for").
  5. Harms and benefits — what each stakeholder could gain or lose.
  6. Map to values — tag each harm and benefit with the values it touches (privacy, trust, ...).
  7. Define the key values — what each value means in this context.
  8. Value tensions — connect two stakeholders whose values conflict and name the value on each side.
  9. Take it into the organization — an owner and next action for each key value and tension.

The board:
  - Rings around the centre: core (inner), peripheral, and excluded (outside the peripheral ring).
    Where a token sits sets its ring; moving it re-classifies it.
  - Tokens: filled = direct, outlined = indirect, dotted plum outline and "?" = hidden or overlooked
    (Yoo's first goal: surfacing hidden, overlooked, or neglected stakeholders).
  - Relationships are arrows; tensions are dashed red curves labelled with the two values.
  - Harms (−), benefits (+), and values show as small chips under each token.
  - The starting point appears in full as a heading strip above the board (click it to edit); the
    centre token shows a short version.
  - Long names: token and centre labels shrink (16px down to 12px) until whole words fit; if a label
    still doesn't fit it ends in "…" and its full text shows on hover or keyboard focus.

Interaction:
  - A palette on the left: drag a Direct / Indirect token onto the rings, or click it (or press Enter)
    to add it to the peripheral ring. Add first, then name (as with physical tokens, which participants
    label themselves): the new token is selected, the cursor goes to its Name field in the inspector,
    and Enter returns to the token on the board. Unnamed tokens read "Name me".
  - Drag from a token's dot to another token to connect them. From step 8, a toggle chooses whether a
    new connection is a relationship or a tension.
  - An inspector on the right edits whatever is selected (centre, token, or connection) and lists the
    values. Every board action is also available here as a form control, so the activity works from
    the keyboard: ring select, "Connect to…", "Tension with…", harm/benefit editors, value tags.
  - Select + Backspace/Delete removes a token or connection.
  - The board stays mounted when the student moves between steps, keeping zoom and selection.
  - Guidance: each step lists what it introduces under "New in this step" on the step card (label +
    where to find it). The matching controls carry a dashed amber outline in that step only (the
    excluded ring is drawn amber; in step 4 the token dots grow and turn amber). Hovering or focusing a
    card item makes its controls pulse; clicking scrolls to them. The card finds controls through a
    data-guide attribute, so it does not depend on how the activity is built.

Worked example: a smart doorbell camera board (a different case from the reading app students are
offered, so it models each step without giving away their answers). "See an example of this step" on
the step card swaps the activity panel to the example: read only, filtered to what exists by the
current step (e.g. step 2 shows only direct stakeholders; definitions appear from step 7), marked
"Example" in the panel header, with "← Back to my board" right beside the badge. The board has a hatched background and a dashed border so it reads as
read only. The student's board is not touched. Always available. The example
is lesson content (ActivityDefinition.example), served like the rest of the lesson.

Your work (activity panel header): Export downloads the current state as a .json file
(format "vsd-activity-export", with the activity kind and state key). Import loads such a file,
rejecting other files or other activity kinds, and asks before replacing existing work.
Start over asks for confirmation, clears the work of every activity sharing the state (all
steps of the board) and their checked status, and returns to the first step. These are generic:
they work for any activity, through the services layer (exportWork, importWork, clearWork).

Saving: the board is one shared state for the lesson (shared stateKey). Each step still has its own
report (status, plus a snapshot of the board when it was saved), so feedback and submissions can be
traced to a step. A step that was submitted shows as in-progress again once the board changes elsewhere.


VALUE SCENARIOS LESSON

The selected lesson is one choice for the whole app: picking a lesson on any tab (Workspace, Prompts,
Versions) changes it everywhere, and the browser remembers it. Switching back to a lesson returns to
the step last open in it. Unsaved prompt edits are kept per lesson, so switching never discards them.

The open step is also one choice for the whole app. A step trail under the tab bar, on every tab,
shows the lesson's steps as dots joined by arrows (o → o → o); the current step's dot is filled
with the lesson's color and slightly larger, and "Step N of M · Title" is written beside the trail,
so color is never the only cue. Clicking a dot opens that step everywhere: the Workspace activity,
the Prompts preview, and the Prompts step questions. Each dot shows "Step N · Title" on hover or
focus, and is labelled "Step N of M: Title" for screen readers. The Workspace's activity list and
Next button move the trail too. On narrow screens the trail wraps.

A second, independent lesson (Nathan, Klasnja & Friedman, 2007): short stories about how a technology
plays out for different stakeholders, once widely used and over many years. Its own steps, saved work
(stateKey "value-scenarios"), example, Export / Import / Start over, and prompts. The learning
workspace header switches between lessons.

Telling lessons apart: each lesson has an accent color and a symbol (Stakeholder Analysis: sage
#A6BAA0 and ◎; Value Scenarios: coral #D26559 and ≡), both from the VSD Lab palette. The color
appears in four places only: the active lesson tab (filled), a band along the top of the step card,
the open step in the activity list (its number in a filled circle, like the trail's dot, and its
title filled and bold), and the activity panel header (filled; it stays in view while working).
The lesson's name and symbol always appear alongside, so color is never the only cue. The workspace ground stays orange.
The Prompts and Versions tabs use the same lesson switcher (active lesson filled with its color),
and the lesson being edited colors the prompt editors' left edge, the preview, the selected version,
and the version details. Each tab keeps its own ground.

Bottom panel (a simple list for now; a time × pervasiveness grid may come later):
  - Left: the technology, and "Whose stories?" (stakeholders, direct or indirect). Optional bridge:
    "Add from my stakeholder map" brings in the named stakeholders from the stakeholder lesson,
    skipping names already listed. The lessons stay independent: nothing else is shared, and the
    bridge reads the other lesson's saved work through the services layer.
  - Right: scenario cards (title, whose story, the story today), then fields added by later steps.

Steps:
  1. Choose the technology.
  2. Whose stories? — at least one indirect stakeholder.
  3. Write a scenario — a person, a place, a moment; scenarios for at least two stakeholders.
  4. Move it forward in time — "Later" in 5 or 20+ years.
  5. Imagine everyone has it — widespread use.
  6. Trace systemic effects — institutions, norms, relationships.
  7. Value implications — values per scenario, each marked harm or benefit.
  8. Compare scenarios — tensions between two scenarios, with a note on the values in conflict.

Worked example: the same smart doorbell camera, as three scenarios (a delivery driver, a passer-by,
a homeowner) with two tensions; read only and filtered by step, as in the stakeholder lesson.


B. PROMPTS TAB

Edit the prompts used to generate AI feedback (open to students; see PRODUCT).
The full Prompts tab spec is in specs/PROMPTS_TAB_SPEC.txt; this section is the summary.

- A short introduction says what the prompts are and that anyone, students included, can change them.

- System prompt: the AI's role, tone, and rules (e.g. "do not give away the answer").
- User prompt: a template filled with activity and student data using variables:
    {{activity_title}}, {{activity_prompt}}, {{objectives}}, {{student_work}}
- Questions to ask: the questions the AI can ask about the work, for every step and for each step,
  sent inside the system prompt (only the checked step's own list).
- A preview that shows the user prompt filled in for the step open in the Workspace.
- Saving creates a new version; it never overwrites an existing one.
- Prompts are kept per lesson (each lesson has its own tutor role and rubric). The lesson switcher at
  the top is the same selection as in the Workspace and Versions tabs.


C. VERSIONS TAB

Track the history of prompt changes:

- List of versions: number, author (a placeholder, "you", until sign-in), date, and a short note.
- Selecting a version shows its full system prompt, questions to ask, and user prompt.
- Placeholders for later: comparing two versions (diff) and restoring an older version.
- Every feedback result records the prompt version that produced it, so results can be traced back
  to the prompts that generated them.


VISUAL STYLE

Adapted from the VSD Lab site (vsdesign.org: home, projects, the lab):
- One flat, muted colour ground per tab, like the site's per-page colours:
  Workspace = orange #D68C45 (home), Prompts = mauve #BAB3BC→#B0A9B2 (projects), Versions = blue #7F9CC7 (the lab).
- Cormorant Garamond for all text; a condensed sans (Barlow Condensed) for the app wordmark.
- Ink #00001C for text, plum #573D52 for links, primary buttons, and focus.
- Large white display titles with a trailing period ("PROMPTS."), and stacked thin white rules as dividers.
- Flat and editorial: square corners, no shadows; panels are light translucent fills with thin white borders.
- Accessibility: white fails contrast on these grounds (about 2.2–2.8:1), so it is only used for large titles
  and rules; all working text is ink (7:1 or higher). Lining numerals are used so "1" does not read as "I".
- Fonts are self-hosted (no requests to Google Fonts), so the app works offline and does not share student traffic.
- Light theme only, matching the site.


RECOMMENDED TECHNOLOGY

- Frontend: React with TypeScript, built with Vite.
- Layout: CSS Grid for the main three-panel arrangement.
- Backend: Python with FastAPI.
- Diagram activities: React Flow for node-and-connection diagrams (also used for the stakeholder token board).
- Freeform canvas activities: React Konva when students need to draw, move, or resize shapes.
- Region highlighting and annotation: Prefer SVG overlays when the visual consists of selectable shapes or regions.
- Backend communication: Use HTTP endpoints for loading activities and saving student work. Add streaming for AI feedback later; use WebSockets only if ongoing two-way interaction is needed.
- Storage: SQLite (or JSON files) to start; move to a hosted database only when needed.

Frontend and backend are siblings so the Node and Python toolchains stay separate and each can be run or deployed on its own.


WHY A BACKEND

Frontend-only is sufficient while everything is mock data. A backend is required once any of the following is true:

- AI feedback is real: the model API key must never be shipped to the browser.
- Prompt versions must persist across devices (each person's versions are their own).
- Real students use the tool: their work and feedback must be stored centrally, not in one browser.

The backend stays thin. It stores and serves data and makes the AI call. It never implements
activity behavior; it treats each activity's state as opaque JSON.


BACKEND RESPONSIBILITIES

The full backend design (groups, sign-in with personal access codes, roles, limits, what is
stored, consent, hosting on the UW server, every endpoint) is in specs/BACKEND_SPEC.txt; this
section is the summary.

Placeholder phase:
- GET  /lessons                        Lesson list (id, title)
- GET  /lessons/{id}                    Lesson and activity definitions
- GET  /activities/{id}/report          Load a student's saved work (with the shared state, if the activity has a stateKey)
- PUT  /activities/{id}/report          Save a student's work (and update the shared state, if any)
- DELETE /activities/{id}/report        Start over (clears the shared state too; consider archiving
                                        instead if student work is research data)
- POST /feedback                        Return a Feedback object (mock for now)
- GET  /lessons/{id}/prompts/versions   Prompt version history for a lesson
- POST /lessons/{id}/prompts/versions   Save a new prompt version for a lesson

Later:
- Fill the user prompt template, call the AI model with the system prompt (with the questions to
  ask inside it; see specs/PROMPTS_TAB_SPEC.txt) and the user prompt, and convert the response
  into the Feedback contract.
- Log every feedback request and response, with its prompt version and the student's rating.
- Stream feedback as it is generated.
- Add sign-in (personal access codes per group), and record each prompt version's owner and role
  (participant, group lead, admin). See specs/BACKEND_SPEC.txt.


DATA CONTRACTS

Defined once in frontend/src/types/contracts.ts and mirrored as Pydantic models in the backend.

- Lesson: id, title, intro, activities[].
- ActivityDefinition: id, kind (diagram | annotation | stakeholder-tokens), title, prompt, objectives,
  optional stateKey (activities with the same key share one state), optional config (activity-specific
  settings, passed through untouched, e.g. { step: 3 }), optional guide[] (what the activity introduces:
  target, label, where; shown on the step card).
- ActivityGuideItem: target (matches data-guide on activity elements), label, where.
- ActivityProps (what an activity receives): prompt, config, savedState, onChange(state).
- ActivityReport (what gets stored and sent for feedback): activityId, kind, status (in-progress | submitted), state, updatedAt.
- Feedback: activityId, source (mock | ai), promptVersionId, generatedAt, summary, items[].
- FeedbackItem: id, tone (praise | suggestion | issue), message, optional targetId.
- PromptSet: system, questions (for every step), stepQuestions (by activity id), user. The questions
  are sent inside the system prompt: every-step ones plus the checked step's own.
- LessonSummary: id, title (for lesson lists).
- StakeholderRef: name, kind (direct | indirect) — stakeholders passed between activities.
- ActivityDefinition.stakeholderSource: optional { stateKey, kind, label } to bring stakeholders in from.
- PromptVersion: id, lessonId, number (within the lesson), author, note, createdAt, prompts.


ARCHITECTURE PRINCIPLES

- Keep coupling low and encapsulation high.
- The app shell coordinates the tabs; the workspace tab coordinates its panels. Neither implements activity-specific behavior.
- Each panel owns its presentation and internal behavior.
- Each activity owns its interaction logic and any canvas library it requires.
- Connect modules using small, explicit data contracts rather than direct dependencies on one another's internals.
- An activity receives its prompt and saved state, then reports changes or a result in a standard format.
- The feedback panel receives a feedback object. Initially, provide it from mock data; later, replace the data source without changing the panel or activity components.
- All data access goes through the services layer, so switching from mock data to the backend changes only that layer.
- Keep shared types and service boundaries explicit. Avoid building a plugin system or extra framework layers until the project needs them.

LEARNING-TOOL CONSIDERATIONS

- Learning objectives: every activity lists what the student should demonstrate; the same objectives are given to the AI as rubric context.
- Feedback should guide, not give away answers (set in the system prompt, which students can change; see PRODUCT).
- Accessibility: keyboard access for activities, screen-reader announcements for new feedback.
- Privacy: student work and feedback logs may be research data (consent, anonymized IDs, IRB / FERPA where applicable).


IMPLEMENTATION PHASES

Phase 1 — Frontend with mock data (current)
- Build the tab shell, the panel layout, resizable panels, and responsive behavior.
- Implement the feedback panel with clearly marked placeholder content.
- Define the activity input/output contract and render an activity through ActivityHost.
- Keep the diagram and annotation activity implementations separate so either can evolve independently.
- Diagram activity uses React Flow: add nodes, drag them to arrange, drag between node handles to connect,
  select and press Backspace to delete. Saved state stays library-independent (nodes with x/y, edges).
- Persist activity state as structured data (localStorage for now) that can later be sent to the FastAPI backend.
- Stakeholder Tokens lesson: nine steps sharing one ring board (see STAKEHOLDER TOKENS LESSON).
- Prompts and Versions tabs with basic structure; saved versions are kept in the browser (localStorage).

Phase 2 — Minimal backend
- FastAPI app with the placeholder-phase endpoints above and simple storage.
- Point the frontend services at the backend.

Phase 3 — Real AI feedback
- Connect the model in POST /feedback, log results with prompt versions, add streaming and sign-in.


OPEN QUESTIONS

- Which AI model / provider?
- Should version tracking also cover lessons and activity definitions, or only prompts?

Decided (details in specs/BACKEND_SPEC.txt):
- Setting: any group of people, a class or a research study; each group is set up by its
  instructor or researcher.
- Prompts are personal: a saved prompt version applies only to its owner's feedback.
- Hosting: a UW server.
