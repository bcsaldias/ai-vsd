VSD Student Learning Workspace — Backend Specs

The detailed spec for the backend: who can use the app, how they sign in, how the AI is called, and
what is stored. ../APP_SPECS.txt covers the core app (WHY A BACKEND, BACKEND RESPONSIBILITIES, the
data contracts); this file covers the design decisions below in detail. The Prompts tab's own
behavior is in PROMPTS_TAB_SPEC.txt.


DECISIONS

- Who uses it: any group of people, a class or a research study. Each group is set up by the
  person who runs it (an instructor or a researcher), with its own codes, limits, and rules.
- Identity: pseudonymous. Each person signs in with a personal access code. The app never asks
  for or stores names or emails; whoever runs the group keeps any link from code to person,
  outside the app.
- Prompts are personal: a prompt version someone saves applies only to their own feedback. Others
  in the group never see or receive it.
- The AI key lives only on the backend. The browser never sees it.
- Hosting: a UW server.


PURPOSE

1. Call the AI model with a key that is never shipped to the browser.
2. Know who is asking, so only people with a valid code use the key, within their limits.
3. Store everyone's work, prompts, and AI interactions centrally, so they can be traced (which
   prompt version produced which feedback) and, for studies, exported as research data.

The backend stays thin, as APP_SPECS.txt requires: it stores and serves data and makes the AI call.
It never implements activity behavior and treats each activity's state as opaque JSON. Anything
that depends on how an activity works (limiting work to a step) happens in the frontend before
the request is sent.


ROLES

  participant   A student or study participant. Uses the app; sees only their own work, prompts,
                and feedback.
  group lead    An instructor (class) or researcher (study). Everything a participant can do, plus
                for their own groups: create codes, set limits, turn codes off, see usage, and
                (studies) export data.
  admin         Runs the server. Creates groups and group leads, sets the overall budget, sees all
                usage.

A person's role comes from their code. A group lead's code is created by an admin; participant
codes are created by the group lead.


GROUPS

A group is a class or a study. Every participant belongs to exactly one group.

Each group has:
  - name and type: "class" or "study"
  - lead(s): the group lead codes that manage it
  - lessons: which lessons its participants see (default: all)
  - daily request limit per participant (default 30 feedback requests a day)
  - group budget: a cap on AI spending per month (requests stop when reached)
  - consent: required for studies (see CONSENT), off for classes
  - active dates: optional start and end; codes don't work outside them
  - data kept for: how long its interactions are kept (see DATA RETENTION)

The type sets sensible defaults; a group lead can change limits and dates for their own groups.


ACCESS CODES AND SIGN-IN

Codes:
  - One code per person, generated by the backend in batches: "make 40 participant codes for this
    group". Codes are easy to type and say out loud, e.g. "river-maple-lantern-42" (three words
    from a fixed list plus a number; about a trillion combinations).
  - The group lead downloads the new codes once, as a CSV (code, participant id, optional label
    column they fill in themselves). The backend keeps only a hash of each code, so codes can't
    be read back later; a lost code is replaced, not recovered.
  - A code can be turned off at any time; its owner is signed out at their next request.

Signing in:
  1. The app shows "Enter your access code" before anything else (when a backend is configured;
     see FRONTEND).
  2. POST /auth/redeem with the code. The backend returns a session token, and who the person is
     to the app: participant id, role, group (name and type), and whether consent is still needed.
  3. The app keeps the token in the browser and sends it with every request
     (Authorization: Bearer <token>). Tokens expire after 30 days of not being used; signing out
     ends the session.
  - Codes are not passwords people chose, so there's nothing to reset. A participant who signs in
    on another device uses the same code and sees the same work.
  - Repeated wrong codes from one address are slowed down (e.g. 10 tries per 10 minutes).

Later, if a group needs verified identity: UW single sign-on (UW NetID) can be added as another
way to sign in. Everything else here stays the same: sign-on maps the person to a participant id.


CONSENT (studies)

- In a study group, the first sign-in shows the study's consent text (written by the researcher,
  stored with the group). Nothing is stored and no AI request is made until the participant
  agrees. Declining signs them out; their code stays usable if they change their mind.
- The consent version and time are recorded with the participant.
- Classes show a short notice instead (what is stored and why), with no blocking step.
- The consent text and procedure follow the study's approved IRB protocol (UW Human Subjects
  Division); this spec doesn't replace that review.


THE AI CALL: POST /feedback

The frontend sends:
  - lessonId, activityId, promptVersionId
  - the student's work, already limited to the step (workUpToStep in the frontend), twice: as
    JSON, which is stored, and in plain language (describeWork), which fills {{student_work}}.
    The backend never converts work itself.
  - the prompts as they stand for this request: system, questions (every step and this step),
    user template

The backend:
  1. Checks the token: an active participant, in an active group, who has consented (studies).
  2. Checks limits: the participant's requests left today, the group's monthly budget, and the
     server's overall budget. Over a limit → a clear message ("You've used today's 30 requests;
     they reset at midnight") and no AI call.
  3. Checks the prompt version belongs to this participant (or is the lesson's starting version).
  4. Builds the request exactly as the Prompts preview shows it: the system prompt with the
     questions inside it (every step, then this step), and the user template filled with the
     activity's title, task, objectives, and the work. Same rules as systemPromptParts and
     templateVariables in the frontend.
  5. Calls the model with the server's key, and turns the reply into the Feedback contract.
  6. Logs the whole interaction (see WHAT IS STORED) and returns the feedback.

Requests and replies are size-limited (e.g. work up to 200 KB, prompts up to 20,000 characters).
The model and key are set on the server (environment variables). Which model is still an open
question (APP_SPECS.txt).


PROMPTS ARE PERSONAL

- Each participant starts from the lesson's starting version (content/<lesson>/prompts.json), the
  same for everyone in the group.
- Saving in the Prompts tab creates a new version owned by that participant. Their feedback uses
  their latest version; nobody else's does.
- The Versions tab shows the lesson's starting version and the participant's own versions only.
- Group leads can see their participants' versions read-only (with usage, later), e.g. to study
  how prompts changed. Participants never see each other's.
- Version numbers are per participant and per lesson (starting version is 1). The numbering
  collision noted in promptService goes away: the backend numbers versions.


WHAT IS STORED

  participants        id, group, role, code hash, created, active, consent (version, time),
                      daily limit override
  groups              name, type, leads, lessons, limits, budget, consent text and version,
                      active dates, retention
  sessions            token hash, participant, created, last used, expires
  work                each participant's saved work per activity, and the shared state per board
                      (what is in the browser's localStorage today)
  prompt versions     owner (participant), lesson, number, note, created, prompts (system,
                      questions, stepQuestions, user)
  feedback requests   participant, group, lesson, activity, prompt version, the exact system and
                      user prompts sent, the work sent (JSON, and the plain-language text used
                      in the prompt), the model and its reply, the Feedback
                      returned, input and output tokens, estimated cost, time taken, time
  ratings             feedback request, item, helpful or not, time

No names, emails, or free-text identity fields. Participants' own writing can still identify them
(a story about their family), so the data is treated as identifiable for privacy purposes.

Storage: SQLite to start (APP_SPECS.txt), in one file on the server, backed up daily. Move to a
hosted database only when needed.


DATA RETENTION, EXPORT, AND DELETION

- Each group sets how long interactions are kept (studies: as the protocol says; classes: default
  the end of the term plus 90 days). Expired data is deleted automatically.
- Study leads can export their group's data (participants, prompt versions, feedback requests,
  ratings) as CSV / JSON, keyed by participant id only.
- A participant's data can be deleted on request by their group lead (e.g. a withdrawn consent);
  deletion removes their work, prompts, interactions, and ratings.
- Class data is for running the class. Exports for research from a class need that class to be
  set up as (or alongside) an approved study.


USAGE AND LIMITS

- Every feedback request records tokens and an estimated cost.
- GET /me returns the participant's requests left today; the Prompts tab shows it
  ("Requests left today: 18").
- Group leads see usage for their groups: requests per day, per participant, cost so far.
- Admins set the server's monthly budget; when it is reached, requests stop for everyone until
  the next month or an admin raises it.


ENDPOINTS

Sign-in and self:
  POST   /auth/redeem                       code → token, participant, group, consent needed
  POST   /auth/consent                      record consent (studies)
  POST   /auth/logout                       end the session
  GET    /me                                who I am, my group, requests left today

Content (from the same content files the frontend uses):
  GET    /lessons                           lessons this participant's group can see
  GET    /lessons/{id}                      a lesson and its steps

Work (the participant's own):
  GET    /activities/{id}/report            saved work, with the shared board state
  PUT    /activities/{id}/report            save work
  DELETE /activities/{id}/report            start over

Prompts (the participant's own, plus the starting version):
  GET    /lessons/{id}/prompts/versions     starting version + my versions, newest first
  POST   /lessons/{id}/prompts/versions     save a new version of my prompts

Feedback:
  POST   /feedback                          see THE AI CALL
  POST   /feedback/{id}/rating              helpful / not helpful per item

Group leads (their own groups) and admins:
  POST   /groups                            create a group (admin)
  PATCH  /groups/{id}                       limits, dates, consent text, lessons
  POST   /groups/{id}/codes                 make N codes; returns the CSV once
  PATCH  /participants/{id}                 turn a code off or on, change its daily limit
  GET    /groups/{id}/usage                 usage per day and per participant
  GET    /groups/{id}/prompt-versions       participants' versions, read only
  GET    /groups/{id}/export                research export (study groups)
  DELETE /participants/{id}/data            delete a participant's data

Every endpoint except /auth/redeem needs a valid token; group-lead endpoints check the role and
that the group is theirs.


FRONTEND

- The backend address is a build setting (VITE_API_URL). Without it, the app runs as today:
  no sign-in, work and prompts in the browser, placeholder feedback. That keeps the public demo
  on GitHub Pages working with no key and no server.
- With it:
  - a sign-in screen ("Enter your access code"), then consent if the group needs it;
  - the tab bar shows who's signed in (the participant id, or a nickname they set) and Sign out;
  - the Prompts tab shows "AI: connected · <model>" and requests left today;
  - the services layer calls the endpoints above instead of localStorage, with the same function
    signatures (activityService, promptService, feedbackService), so no component changes.
- First sign-in on a browser that already has work or prompt versions saved locally: offer to
  bring them into the account ("Bring in the work saved in this browser?"), once.
- Group-lead screens (codes, usage, export) come after the participant flow works, as a separate
  page only group leads can open.


HOSTING ON THE UW SERVER

- The FastAPI app (backend/ in the repository) runs behind the server's web server over HTTPS,
  e.g. https://<server>.uw.edu/ai-vsd/api.
- Secrets in environment variables, never in the repository: the AI key, a secret for hashing
  codes and tokens, the admin bootstrap code.
- The frontend can stay on GitHub Pages: the backend allows requests only from the app's own
  addresses (CORS: https://bcsaldias.github.io and local development). Alternatively the UW
  server can serve the frontend too, which keeps everything on one UW address.
- The SQLite file and its daily backups stay on the UW server. Any study data handling follows
  UW requirements for the data's classification (to confirm with UW-IT and the IRB).
- Logs: requests and errors, without the work or prompts in the log lines (those go only to the
  database).


BUILD ORDER

1. Sign-in with codes, groups, POST /feedback with limits and logging; the frontend sign-in
   screen and feedbackService calling the backend. This is the minimum to use the key safely.
2. Work and prompt versions on the server (personal prompts), and bringing in browser data.
3. Group-lead page: codes, usage, read-only prompt versions, export, deletion.
4. Later: UW NetID sign-on, streaming feedback.


OPEN QUESTIONS

- Which AI model (and provider)? Decides the request format in step 4 of THE AI CALL and cost
  estimates.
- The UW server: which machine and who maintains it, OS and Python version, how HTTPS and the
  address are set up, and where backups go.
- Default limits: requests per participant per day, and monthly budgets per group and overall.
- Studies: the IRB protocol's consent text, data classification, and retention period.
- Classes: may instructors see individual students' interactions, or only totals? (FERPA)
